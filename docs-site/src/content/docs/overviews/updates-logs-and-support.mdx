## Updating

**After the first install, the app installs its own updates.** Once per launch
it asks the website whether a newer release exists. When one does, the notice
can do the update: it fetches the installer for the way *this* copy was
installed — the `.deb`, the `.rpm`, the Windows Setup or the `.dmg` — checks
it against the checksum the release publishes, hands it to Setup, Finder or
your package manager, and closes so that can happen. (Installing an update on Windows used to end
with a crash report for a program already on its way out, because quitting to
the installer took a different road out than closing the window; it no longer
does. The update itself was never affected.) On Windows, Setup offers
to reopen the app when it has finished; on macOS and Linux you start it again
yourself.

**Nothing is installed behind your back.** You get the ordinary installer
window and can still say no to it. A download that does not match its
checksum is thrown away. Where the app cannot tell how it arrived, it opens
the download page instead, exactly as before.

It will not close over unsaved work: a file that changed on disk while you
were editing it stops the update and says which one.

Nothing is code-signed yet, so the installer will ask on Windows and macOS the
same way it did the first time. [Installing](/setup/installing/) says what
each platform asks, and what to do about the one refusal that is not a click
away.

## Engine fixes

**The part of the app that plays and compiles campaigns can be fixed without a
new installer.** A fix is fetched in the background, checked against a
signature before it is trusted, and used from the next launch. If the app
crashes with a fix, the fix is set aside automatically. A fix never changes
what the app can do.

A button in the app bar shows while a fix is arriving, and again once it is
ready, with the version it moves to. Everything about it lives under
**Settings ▸ Updates**: *Engine updates* turns the fetching off, and *Use the
bundled engine* removes the fixes already fetched, so that the next launch
uses the engine the installer brought. What the request carries is listed in
[What the app sends](/about/what-the-app-sends/#engine-fixes-unless-you-switch-them-off).

Settings is split into pages: *General* holds how the app looks, reads and
plays, *Data control* holds usage statistics, and *Updates* holds engine fixes.
*Agents*, *Support* and *About* are pages of the same dialog, opened by the
gear on every screen. The app bar keeps only what has news: an available
update, and the agents mark while an assistant is connected or could not reach
the app.

## The session log

Ripple Effect keeps a diary of each run, and **it stays on your machine**.
Nothing uploads it, there is no switch that would, and when you want to report
a bug you decide what to hand over.

**One thing can carry a copy of it away, and it asks you first.** If the app
crashes, the next launch shows you the crash report it saved — every file in
it, its size, and what each one contains — and sends it only if you answer
*Send report*. The session's logs are among those files. There is no
&ldquo;always send&rdquo; setting and no &ldquo;never send&rdquo; one:
the question is asked once per crash, at the moment you can actually see what
it is about, and whichever way you answer is final for that report. [What the
app sends](/about/what-the-app-sends/) goes through it in full.

**Usage statistics are opt-in, and off until you switch them on.** Nothing
counts what you do, how often you open a board or how long you spend in one.
From 1.5 the app can send anonymous statistics — whether it was in use on a
given day, the day, a random identifier for the installation, the app's version
and your operating system — and it asks once, with the complete list in front
of the question rather than behind a link, neither answer preselected,
switchable off afterwards, and carrying nothing you wrote. The switch is
**Settings ▸ Data control ▸ Usage statistics**: on, the app records once a day that this
installation was in use, with its version and your operating system's family,
under an identifier shown in the row, which also lists everything that is
sent. Nothing is sent until it has been on for an hour. Switching off destroys
the identifier, so nothing already sent can be tied to you again.

**A session is a folder.** What the app records about a run lives in a folder
named by a short id: the log, a separate file for each kind of crash, and what
build you were on. The Rust engine, the part that plays and compiles
campaigns, keeps its own `engine.log` in that folder with the same redaction,
and a crash in it records the file and line it came from, even in a release
build. A compile is written down on both sides with the same number on it, so
the two halves can be read together. A crash writes what happened and closes
off the session log in one go, so the file is complete even when the app is
not; the two background workers that could once fail silently (version control,
and agent traffic on Windows) now write down that they failed.

**It also notes what the app asked of the network, and of an agent.** Checking
for an update, fetching the contributor list and downloading an installer each
leave a line saying where the request went, what came back and how long it
took. Addresses are recorded without anything after the `?`, and no response
content is written. Every tool call, resource read and prompt an MCP client
makes leaves a line too: which client, which tool, which argument *names*
(never their contents), how long it took and whether it worked.

**Nothing is dropped, and a log cannot delete itself.** A message with a line
break in it, such as a Python traceback, can no longer make the next launch
read a problem session as fine and remove it. Warnings and above reach the
file at once with the run-up before them, and a very large run continues into
a second file rather than one nobody can attach to an issue.

**It tidies up after itself.** A session where nothing went wrong is deleted
the next time you start the app, so the folder holds the runs worth something
and not a file for every time you opened a project. If the app falls over
before it can write its own verdict, the next launch reads that file properly
rather than guessing.

**Private things are taken out before anything is written down.** Your
username and home folder, the location of the project you have open, e-mail
addresses, network addresses and anything shaped like a password or a key are
replaced, including e-mail addresses with accented or non-Latin local parts
and account names ending in an accented letter, which earlier builds wrote
down untouched, so that is worth knowing if you have sent logs in. Times are
recorded in UTC rather than your local clock. No list of
rules can know that a board's name is private, so a glance before you post is
still worth it.

The logs live in the app's own support directory — the platform's application
data folder. **Help ▸ Troubleshooting ▸ open this session's folder** opens the
one you are in.

## Reporting a bug

**Settings ▸ Support**, or *Support and feedback* in the Help menu, opens the
support page. **Reporting a bug
fills the form in for you**: the version, your operating system, and which
installer this copy came from arrive already answered, along with the
technical details, so a report starts from what you actually saw rather than
from four questions. It opens the right form in the public support
repository, [`ripple_effect_support`](https://github.com/ConnectingTheDots-DCWK/ripple_effect_support),
which is also where questions and feature requests go.

**Links the app opens go through `ripplefx.app`.** Reporting a bug, asking a
question, the survey, the documentation, the licence and the Privacy Notice
each open an address on the website, which sends you on to where that thing
lives today, so a link in this version keeps working if the place moves.

Under *What to attach*, **Save this session as a zip** packs the session's log
and reports into one file you can attach to an issue, and the page shows the
session's id so a support thread can be about the right one. Copying the
package details and the device details, and opening this session's folder, are
under **Help ▸ Troubleshooting**; *Show every tip again* is in the Help menu
itself. All of them are in the command palette too.

**The documentation is one click from the app.** *Documentation* leads the
pointers in the About box, and the panels that used to explain a feature from
scratch (the variables panel, the agents page, the Python sandbox, the export
dialog, the metadata editor and the state machine editor's bar) now say what
you are looking at and link the page that carries the rest.

## Messages

The **Messages** panel is a different thing from the log, and the two are kept
apart on purpose. Messages is what the app says to *you* about *your folder*:
a translation that has fallen behind, a picture a passage points at that is
not there, a board with no way in, a file written by a newer version. It is
scoped to the open project and cleared when another one opens.

Messages cluster by what they are about (Boards, Translations, Version
control), with a count on each heading you can fold away, or by how loud they
are if you would rather see everything broken first. Three chips above the
list turn problems, cautions and records on and off, and both choices are
remembered. A message from the engine wears its code, which opens the page
that explains it (see [Diagnostics](/reference/diagnostics/)); clicking one
that names cards opens the board and lifts those cards out of the canvas. For
the one check that can be wrong about a deliberate choice, the row has an *I
meant that* tick, and it stays ticked.

The log is
what the app says about *itself*, for whoever reads a bug report.

## Files from a newer version

A project file written by a newer Ripple Effect is never half-read. An older
copy of the app says it cannot read the file, tells you to update, and writes
nothing to it — a strip across the top of the project says what could not be
read, and Messages keeps the note with the file's path. This holds for the
index, the project's settings, a component, a board and a saved game. Things
that only cache something — a bundle's translation timestamps, the list of
recent projects — rebuild by looking at the folder again, so those are never a
reason to stop.
